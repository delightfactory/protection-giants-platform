# Production Order / Lot / Roll Foundation

## Purpose

This cube establishes the first complete PPF production path after Product Foundation. It creates an immutable production record and one database record for every physical roll without introducing transfer, activation, warranty, procurement, shipping, or label-template workflows.

## Included scope

- Admin-only production-order registry.
- Production-order creation for active, production-ready PPF Products.
- One to fifty Lots per order.
- One to 10,000 total rolls per order.
- Atomic and idempotent creation of the Production Order, Lots, and physical Roll records.
- Historical snapshot of the Product identity and production-critical specifications at generation time.
- One-SKU/one-physical-spec protection after a Product enters operational production.
- Database-enforced Order → Lot → Roll lineage consistency.
- System-generated production order number.
- System-generated Lot numbers.
- System-generated internal Roll serials.
- System-generated independent ERP serial per Roll.
- Paginated Production Order and Roll registries, 100 records per page.
- Exact/prefix identity search by Production Order number, internal Roll serial, or ERP serial.
- Production-order review with Lot breakdown and Roll preview.
- Printable multi-page Production Order summary based on the historical snapshot.
- Audited irreversible void path for an order created in error, without deleting or recycling generated identities.

## Deliberately excluded

The following belong to later cubes and must not be added here:

- transfer or ownership history;
- scan-confirmed transfers;
- installation-center roll opening/claiming;
- activation codes or activation QR behavior;
- customer warranty records;
- claims or issue reporting;
- sticker/label layouts and bulk label PDFs;
- procurement, shipping, invoice, or general ERP workflows.

## Data model

### `production_orders`

One immutable header for a production operation. It references exactly one Product and records:

- internal idempotency request key;
- system order number;
- production date;
- optional source reference;
- optional notes;
- total physical-roll count;
- creating administrator and timestamp;
- audit status: `generated` or `voided`;
- void reason, administrator, and timestamp when voided;
- Product/SKU snapshot captured at generation: code, name, version, width, length, thickness, weight, and origin.

The snapshot is intentionally narrow. It protects historical production and future label reprints from later Product edits without introducing a generalized Product-versioning subsystem. Warranty policy is not snapshotted here; the Warranty cube owns the warranty-policy snapshot when a warranty is actually created.

### `production_lots`

The breakdown inside one Production Order. Every Lot references the same Product and its parent order and records:

- system Lot number;
- order-relative Lot sequence;
- optional external/source Lot reference;
- number of Rolls in that Lot.

A composite foreign-key contract guarantees that a Lot cannot point to an Order while claiming a different Product.

### `rolls`

One row equals one physical PPF roll. Each Roll records:

- Product;
- Production Order;
- Production Lot;
- sequence inside its Lot;
- unique internal Roll serial;
- separate unique ERP serial.

Composite lineage constraints guarantee that the Roll Product, Order, and Lot always describe the same production hierarchy. No activation or warranty identifier is stored on the Roll in this cube.

## Product specification lock

The platform decision is one SKU = one fixed physical Product specification. Therefore, once a Product has at least one `generated` Production Order, the database prevents changes to:

- canonical Product code / SKU;
- Product type;
- version/model identity;
- width;
- length;
- thickness;
- weight;
- country of origin.

Non-physical content such as Product name, marketing/technical copy, features, assets, reference price, publication state, care instructions, and warranty policy can still evolve independently.

If all Production Orders for a Product are voided because they did not represent operational production, the physical specification can be corrected again. Every voided Production Order still retains its own historical snapshot, so the audit record does not change.

A materially different physical specification must be created as a new SKU rather than silently changing an SKU that already has operational Rolls.

## Identifier format

Identifiers are generated by the database, never typed by the operator.

- Production Order: `PG-PO-YYYYMMDD-NNNNNNNN`
- Lot: `PG-L-YYYYMMDD-NNNNNNNN-LL`
- Roll: `PG-R-YYYYMMDD-NNNNNNNN-LL-RRRR`
- ERP serial: `ERP-XXXXXXXXXXXXXXXX`

The production sequence is global and monotonic. Gaps are acceptable because failed/rolled-back database transactions may consume sequence values; uniqueness and traceability are more important than gap-free numbering.

## Atomic and idempotent creation contract

All production creation goes through `public.create_production_order(...)`.

The function:

1. verifies that the caller is an active administrator;
2. requires a unique request id generated for the form attempt;
3. serializes retries that carry that same request id;
4. returns the already-created Production Order when the same administrator safely retries the same request instead of generating duplicate identities;
5. rejects reuse of that request id by a different administrator;
6. verifies that the Product is active, PPF, and contains the production-critical specification fields;
7. validates the Lot JSON shape, Lot count, integer quantities, total quantity, and optional reference lengths;
8. captures the Product identity/specification snapshot;
9. generates the order identity;
10. inserts the Production Order;
11. generates all Lots;
12. generates every physical Roll and its identities;
13. commits only if the entire operation succeeds.

If any validation or insert fails, the transaction rolls back and no partial Production Order, Lot, or Roll is retained. A browser double-tap or safe network retry using the same request id resolves to the same Production Order and cannot allocate a second set of Roll identities.

If the database completed a request but the application could not confirm the response, the retry page first resolves the same request id against the current administrator. If the order already exists, the operator is redirected directly to that order with a recovery confirmation instead of being shown a misleading blank form.

Authenticated application users have read access only when RLS confirms an active administrator. Direct Data API insert/update/delete access is not granted for the production tables, including to administrators. This keeps controlled RPCs as the only normal mutation paths.

## Concurrency contract

Production Order insertion locks and re-checks the Product definition at the database boundary. The historical snapshot must still match the current active PPF Product at insertion time.

This prevents a concurrent Product edit/archive and Production Order creation from producing a mixed state. Either the Product change completes first and the creation uses the resulting coherent definition, or the production insertion wins and a conflicting physical Product change is rejected by the produced-SKU lock.

## Void contract

A generated production order is never edited or deleted. If the operator created an order in error or the represented production did not actually occur, an active administrator can call `public.void_production_order(...)` with a mandatory reason.

Voiding:

- changes only the audit lifecycle from `generated` to `voided`;
- records who voided it, when, and why;
- keeps the Order, Lots, internal Roll serials, and ERP serials permanently reserved and visible;
- is idempotent and cannot reactivate the order.

Any later transfer, activation, warranty, or label-execution flow that treats a Roll as operational must require its parent Production Order to remain `generated`. Voided records remain available for audit and printing but are not operational stock.

## Registry and search contract

Both Production Order and Roll registries use explicit 100-record pages rather than silently truncating the data set. Previous/next navigation preserves the active filters.

Pagination uses deterministic ordering with unique tie-breakers. This is particularly important for Rolls because thousands of rows generated by one transaction can share the same `created_at` value.

Registry indexes match the newest-first ordering used by the application. Full generated identities use indexed equality lookups; partial identity input is treated as a prefix search rather than an arbitrary contains search. This preserves the simple operator workflow without turning large registries into avoidable full-table scans.

## UX contract

The operator only provides information that humans actually know:

- Product;
- production date;
- optional source reference and notes;
- Lot quantities;
- optional source Lot references.

The UI calculates the live Lot and Roll totals before confirmation. It does not ask operators to invent order numbers, Lot numbers, Roll serials, ERP serials, or the internal request id.

Production Orders are intentionally not editable after generation because their identifiers represent physical Rolls. A deliberate void control is provided for genuine creation mistakes. The detail page is a review/audit surface, while the paginated Roll registry is the scalable search/browse surface for large orders.

If an administrator tries to alter the physical specification of an SKU that already has operational production, the Product edit flow returns a clear instruction to create a new SKU instead of exposing a database error.

The default production date is calculated in the platform operating timezone (`Africa/Cairo`) rather than server UTC, while remaining editable by the operator.

The printable order supports multi-page Lot tables and explicitly repeats the table header when the browser paginates a long document.

The mobile bottom navigation remains limited to its established five primary items. Production is reachable from the operations home on mobile and directly from the desktop sidebar, avoiding a crowded six-tab mobile bar.

## Verification

`node scripts/verify-production-foundation.mjs` is executed by Database Quality CI after a fresh local migration rebuild.

It verifies:

- successful atomic creation;
- repeated submission of the same request id returns the same order and creates no duplicate order/Lot/Roll identities;
- exact Lot and Roll counts;
- generated identifier formats and uniqueness;
- historical Product snapshot values do not drift after Product edits;
- operational production locks the SKU physical specification;
- non-physical Product content remains editable;
- voiding all operational production permits a physical correction without changing the historical snapshot;
- incomplete Products cannot enter production;
- direct insert/update/delete attempts cannot bypass controlled production mutation paths;
- dealer accounts cannot read, create, or void production data;
- invalid Lot input does not leave partial production records;
- audited voiding keeps all generated Lots and Roll identities;
- repeated void requests are safe and idempotent;
- archived Products cannot receive new production orders.

`node scripts/verify-production-boundaries.mjs` separately exercises closure boundaries that should not be reduced to code inspection:

- actual generation of a 10,000-Roll Production Order;
- persistence of exactly 10,000 physical Roll rows and the `10000` Roll-index identity edge;
- successful 50-Lot order generation;
- rejection of 51 Lots;
- rejection of a 10,001-Roll total;
- prevention of idempotency-key reuse by another administrator;
- rejection of an invalid void reason;
- dealer RLS denial across Production Orders, Lots, and Rolls.

The committed Supabase TypeScript types are also regenerated and compared in CI.
